# 회사 양식 보고서 PPT

## 목적
어떤 원본을 넣어도 **내용은 빠짐없이 지키면서** 회사 보고 양식의 **한눈에 읽히는 PPT**로 바꾼다.
예쁜 PPT 생성기가 아니다. 진짜 가치는 원본을 정확히 읽고 구조화하는 것, 그리고 그 과정에서 수치·사진을 잃지 않는 것이다.

## 처음 한 번 (설치 직후)
이 스킬은 **폴더 전체**(SKILL.md + references/ + scripts/ + package.json + requirements.txt)로 동작한다. SKILL.md만 있으면 틀·부품·검사·완료 관문이 없어 결과가 부실해진다.
- 설치 위치: Claude Code는 `~/.claude/skills/company-report-pptx/`(Windows: `%USERPROFILE%\.claude\skills\company-report-pptx\`), Gemini CLI는 `gemini skills install company-report-pptx.skill`.
1. 스킬 폴더에서 `npm install` (pptxgenjs를 이 폴더 안에 설치 — 전역 설치로는 deck.js가 못 찾을 수 있음)
2. `pip install -r requirements.txt` → `python -m playwright install chromium` (막히면 Edge 사용)
3. `python scripts/check_env.py` 가 "환경 준비 완료"를 출력하는지 확인. 이후 스크립트가 실패하면 먼저 이걸 다시 돌린다.

## 시작 전에
`references/author-preferences.md`를 **먼저 읽는다.** 사용자에게 답하는 형식, 보고서 독자 기준(상무·파트장), 확정된 양식 결정이 들어 있다. 이 기준은 대화 중 사용자가 다르게 말하면 그 말을 따른다.

## 세 가지 원칙
1. **내용은 버리지 않는다** — 수치·사진은 삭제 금지, 위치만 정한다(본문 / 주석 / 유첨). 사진은 어떤 설명의 근거인지 연결한다. 연결은 추측하지 않는다.
2. **양식은 회사 그대로** — 헤더 4요소·박스 틀·레이아웃 좌표는 `scripts/deck.js`가 그린다. 직접 좌표를 계산하거나 고정 영역을 바꾸지 않는다.
3. **박스 안은 읽히게 자유롭게** — 보는 사람이 물어볼 질문(몇 건? 어디까지? 언제 누가?)에 문장을 읽기 전에 답하는 디자인.

## 모드 선택
| 사용자 요청 | 모드 | 하는 일 |
|---|---|---|
| 새로 만들기, 자료 변환 | **생성** | 1~4단계 전부 |
| "이 PPT처럼", 지난 보고서 + 새 데이터 | **참조** | 첨부 PPT의 차트 종류·배치·카드 구성을 따르고 데이터만 교체. 데이터 개수가 달라 형식이 안 맞으면 바꾸지 말고 먼저 알린다. 고정 영역은 항상 deck.js 기준 |
| "A3로", "PDCA로", "종결 보고", 시장 불량·클레임 등 대책·효과까지 관리할 이슈 | **A3** | `references/a3-mode.md`를 따른다. 1장 = `D.a3Slide` 8칸(문제→현상→목표→원인→대책→실행→효과 확인→표준화), 2장~ = 칸별 근거. 모르는 칸은 비워서 [확인 필요]로 드러낸다 |
| "공부용으로", "이해하기 쉽게 정리", 내가 배워야 할 주제 | **학습** | `references/learning-mode.md`를 따른다. 웹 검색으로 보충, 장 수를 줄이지 않고 그림 위주, 자가점검 질문 포함 |
| "N장 그림 개선해줘", "이 박스만 HTML로" | **업그레이드** | 아래 '선택 업그레이드' 절차. 해당 박스만 바꾸고 나머지는 그대로 |
| "검토해줘", 넘겨받은 문서 판단 | **검토** | 1단계 ①~③ + 원본 요약까지. 결과는 회사 양식 2단 한 장(좌: 원본 요약, 우: 문제점·빠진 데이터·확인 질문) + 필요시 회신 메일 초안. 원본 내용/검토 의견/AI 추정을 구분하고 지적마다 원본 위치 표시 |

참조 모드가 아닐 때는 **예시로 받은 보고서의 표·구조를 따라 하지 않는다.** 내용에 맞게 패턴을 고른다.

## 작업 순서 (생성 모드)

### 1단계 — 원본 분석·구조화 → 사용자 확인
사용자가 **상위 모델이 만든 `storyboard.md`**(와 `research.md`)를 주면 1단계를 새로 하지 않는다. `references/handoff-storyboard.md`의 확인 항목만 점검하고 바로 2단계로 간다(실행 도구의 모델이 가벼울 때 쓰는 방식).
원본에 사진·그림이 있으면 먼저 `python scripts/extract_assets.py 원본 assets`로 번호(P01…)를 붙여 꺼낸다(PDF 조각 그림·엑셀 회전·PPT 회전 자동 처리, 캡처 쪽은 쪽 단위). 사진 목록은 이 번호로 관리한다.
원본이 **손필기·스캔 이미지**이거나 **수식(회로 계산)**이 있으면 `references/handwriting-and-math.md`를 같이 따른다(구역 판독 → 잘라내기·overlay 확인 → 수식 LaTeX화·검산).
먼저 **보고 대상·목적**(본인 이해용 / 상사 보고 / 대외 설명)을 확인한다. 대상이 사내가 아니면(가족·아이 학습 자료, 개인 모임 등) 회사 양식이 오히려 안 맞을 수 있으니 그 점을 짚는다. 목적에 따라 핵심 메시지 톤이 달라진다. 본인 이해용은 중립적으로, 작성자 의견은 '의견' 표시로 사실과 분리한다.
`references/source-analysis.md`를 읽고 따른다.
원본 목록표 → 사진 목록 → 빈칸 질문 → 스토리보드를 만들어 보여주고 **OK를 받은 뒤** 2단계로 간다.
외부 자료가 필요하면 쓰고 있는 AI 도구의 웹 검색 기능으로 찾고 출처를 남긴다(실물은 실제 사진, 규격 조항은 실제 원문으로 확인. 관련 리서치 스킬이 설치돼 있으면 같이 사용).
- **웹페이지 내용이 비어 있거나 짧으면**(요금·운영시간·공지가 안 보임, "JavaScript를 켜세요" 문구) 그 페이지는 JS로 그려지는 페이지다. 포기하거나 추측하지 말고 `python scripts/fetch_page.py URL [--selector main] [--click "더보기"]`로 실제 브라우저에서 열어 읽는다. 공식 사이트의 날짜·가격은 이 방법으로 확인한 값을 우선한다.
- 조사 결과는 `research.md`에 **출처·핵심 수치만** 짧게 정리해 두고, 이후엔 원문 대신 이 메모를 본다(같은 페이지 반복 조회·긴 원문 재독 금지).

### 체크포인트 — 스토리보드와 함께 한 번만 묻기
원본 분석이 끝나면 **기본값으로 짠 스토리보드**와 함께 질문을 한 번에 보낸다. 질문은 최대 3개, 각 질문에 기본값을 붙이고 "답 없이 '진행'이면 기본값으로 만든다"고 적는다.
- 묻는 기준: **답에 따라 장 구성이나 핵심 메시지가 바뀌는가.** 바뀌면 묻고, 아니면 기본값으로 진행 후 보고에 적는다.
- 꼭 묻기: 보고 대상(원본에서 명확하면 생략), 원본 없이 만들 때의 핵심 조건(예산·선호 등), 원본 내부 불일치를 어떻게 쓸지.
- 기본값 제시: 압축 vs 시각화, 애매한 사진 연결, 날짜 표기.
- 묻지 않고 처리 후 보고: 개인정보 제외, 날짜 형식 차이, 조각 이미지 처리.
- 사용자가 "바로 만들어"라고 하면 질문을 생략하고, 결과 보고에 가정 목록을 남긴다.
- 보고 대상의 **기본값은 "상무까지 올라가는 보고"**다(사용자의 직속 상사가 그대로 위로 올릴 수 있는 형태). 다른 대상이면 그때만 바꾼다. 작성 규칙은 `references/writing-style.md`의 '두 층 독자' 절.

### 2단계 — PPT 생성
`references/layouts-and-boxes.md`, `references/writing-style.md`를 읽는다.
`scripts/deck.js`로 장을 만들고, 반환된 `boxes[i].inner` 영역 안에만 내용을 그린다.

```js
const D = require("<스킬경로>/scripts/deck.js");
const pres = D.createDeck();
const { slide, boxes } = D.slide(pres, {
  title: "오븐레인지 릴레이 접점 융착 분석",
  message: "접점 용량 부족이 유력 원인, 상위 용량 대체 검토 착수",
  sub: "9월 회수품 12건 분석 기준 / 원인 확정은 11월 재현시험 후",
  layout: "2-55",                       // "1" | "2-55" | "2-64" | "2-73" | "3"
  boxes: [{ title: "회수품 원인 분류", msg: "12건 중 7건이 접점 용량 부족 패턴" },
          { title: "판단 및 조치",   msg: "제조 불량은 배제, 재현시험과 대체 검토 병행" }],
  source: "※ 출처: ○○ 분석 보고서(10/28)",   // 선택
  notes: "원본 항목 #2 #5 #8~11, P1",         // 추적용
});
const L = boxes[0].inner;   // {x,y,w,h} 인치. 이 안에만 그린다
slide.addChart(pres.charts.BAR, data, { x: L.x, y: L.y, w: L.w, h: L.h - 0.3 /* ... */ });
D.boxNote(slide, L, "※ 분류 기준: 접점 표면 분석 / 상세: 유첨 1");
D.save(pres, "결과.pptx");   // 페이지 번호 "현재 / 전체"를 넣고 저장 (pres.writeFile 직접 호출 금지)
```
- **박스 안은 먼저 부품으로 채운다.** 직접 좌표를 짜는 건 부품으로 안 되는 그림(차트·흐름도·지도)일 때만. 부품은 높이를 박스에서 나눠 계산하므로 넘치지 않는다.
  | 부품 | 용도 |
  |---|---|
  | `D.cards(pres, s, A, [{tag, red, title, big, body}])` | 결론·추천·함정 카드 세로 배치 |
  | `D.rows(pres, s, A, [[라벨, 설명, red]], {lw})` | 라벨-설명 행 목록 |
  | `D.kpis(pres, s, A, [{num, unit, label, red}])` | 큰 숫자 카드 가로 배치 |
  | `D.steps(pres, s, A, [[제목, 설명, red]])` | 번호 단계 |
  | `D.checklist(pres, s, A, [[항목, 설명, "필수"/"선택"]])` | 체크리스트 |
  | `D.table(pres, s, A, head, body, {colW, hi, rowH, judge, num})` | 표(hi 강조 행, judge 판정 열 자동 색 OK·NG, num 숫자 열 오른쪽 정렬, 박스를 넘으면 오류로 멈춤, 반환값 = 표 아래 y) |
  | `D.splitV(A, [비율...])` / `D.splitH(A, [비율...])` | 박스 안 영역을 위아래·좌우로 나누기 |
  | `D.equation(pres, s, A, png, [w,h])` | 수식 이미지를 원래 크기로 (render_math.py 결과) |
  | **시각화 부품** | |
  | `D.chartBar(pres, s, A, {labels, values, unit, highlight, related})` | 원인·항목 순위 (강조 1개 메인색, 관련 연한색, 나머지 회색) |
  | `D.chartLine(pres, s, A, {labels, series, unit, target})` | 월별·주별 추이 + 기준선 (기준선을 쓰면 점마다 값 표시는 생략되니 핵심 값은 `kpis`로 옆에) |
  | `D.chartDonut(pres, s, A, {labels, values, center, centerSub, unit})` | 구성비 + 가운데 큰 숫자 + 순위 범례 |
  | `D.timeline(pres, s, A, [{date, title, desc, red}])` | 경과·일정 |
  | `D.flow(pres, s, A, [{title, desc, state}])` | 진행 단계 (done/now/plan/risk), 원인 미확정 4단 구조 |
  | `D.matrix(pres, s, A, {xLabel, yLabel, items, goodZone, goodText})` | 선택지 비교 2×2 위치도 (x·y는 0~1) |
  | `D.annotate(pres, s, A, {px, py, text, dx, dy, w, red})` | 차트·그림 위 핵심 지점 주석. 위치는 `chartLine(...).point(i, 값)` / `chartBar(...).barEnd(i)` 반환값을 그대로 펼쳐 넣는다 |
  | `D.figureFit(pres, s, A, png, kind)` | `render_html.py --fit`로 영역 크기 그대로 그린 그림을 1:1로 넣기 (글자 크기 일치) |
  | `D.a3Slide(pres, {title, message, sub, plan:[...], act:[...]})` | **A3 모드** PDCA 8칸 한 장(좌 Plan ①~④ / 우 Do·Check·Act ⑤~⑧). 빈 칸은 빨간 점선 [확인 필요]. `draw:true` 칸은 반환 `areas[칸]`에 차트를 그림 |
  | `D.figure(pres, s, A, png, [w,h], kind)` | HTML 그림·사진 넣기 + 종류 표시(kind: diagram, map, gantt, calendar, photo …) |
  부품 호출법이 헷갈리면 `examples/catalog.js`(가상 데이터 8장 견본, `node examples/catalog.js 견본.pptx`)의 **코드 쓰는 법만** 참고한다. 장 구성·문구·데이터는 따라 하지 않는다.
  `A`는 `boxes[i].inner` 또는 split 결과. 빨간색(`red`)은 문제·리스크·1순위 강조에만.
- 색은 `D.THEME`만 쓴다(회사 색). 차트는 PPT 기본 차트로(수정 가능).
- PPT 도형으로 그리기 어려운 개념도·흐름도·원리 그림은 HTML(순수 SVG/CSS)로 그려 `python scripts/render_html.py 그림.html 그림.png`(Playwright)로 고해상도 렌더링 후 `D.photo`로 넣는다. 그림 영역은 `id="figure"`. 사내 PC에서 브라우저 다운로드가 막히면 `--channel msedge`. HTML 그림의 색은 직접 쓰지 말고 `D.THEME` 값을 CSS 변수(:root{--main:#...})로 넣어 쓴다 — 메인색을 바꿨을 때 그림 색도 같이 바뀌게.
- 글자 예산 경고(`[글자 예산 초과]`)가 나오면 문장을 줄인다.
- 스토리보드의 원본 항목 번호를 각 장 `notes`에 남긴다.
- 유첨은 같은 양식(보통 `layout: "1"`), 원본 정밀도 그대로, 본문과 "상세: 유첨 N" / "→ N번 장 근거"로 연결.
- 표지: 사용자가 **회사 표지를 직접 붙이는 것이 기본**. 이때는 표지를 만들지 말고 `D.save(pres, 파일, { reserveCover: true })`로 저장한다(전체 장 수에 표지 1장을 미리 포함 → 표지를 붙이면 본문 첫 장이 '2 / 전체'로 맞음). 표지를 만들어 달라고 할 때만 `D.cover(...)` 사용.
- 색: 파란색 글자·선은 `THEME.main`, 본문 박스 소제목 띠 배경은 `THEME.band`. 회사 색 확인 후 이 두 값만 바꾼다. 연한 보조색(`tint`, `light`, `mid`)도 새 메인색 계열로 같이 맞춘다.
- 폰트를 회사 전용 글꼴로 바꿀 때는 `THEME.font` 한 곳만 바꾸고, `check_linebreak.py`의 글자 폭 기준을 실제 렌더링과 한 번 대조한다.

### 부품은 바닥, 핵심 장은 맞춤 (단조로움 방지)
- 부품은 **품질의 바닥**을 보장하는 도구다. 모든 장을 부품 하나씩으로만 채우면 문서가 견본처럼 단조로워진다.
- 스토리보드에서 **핵심 장 1~2개를 `[맞춤]`으로 표시**한다(보통 1장 요약과 가장 중요한 근거 장). 맞춤 장은 내용에 맞게 설계한다:
  - 차트 + **주석(annotate)**: "어디를 봐야 하는지"를 짚는다 — 대책 적용 시점, 기준 초과 지점, 최대 원인
  - 부품 **조합**: 한 박스 안에 차트 + 숫자 + 주석, 사진 + 불량 부위 표시 + 판정 칩
  - **HTML 도식**: 원리·관계·흐름처럼 부품에 없는 구조는 직접 그린다(`render_html.py` → `figure`)
- 같은 부품을 쓰더라도 **박스 메시지·강조 대상·주석**이 내용마다 달라야 한다. 차트 종류를 바꾸는 것보다 무엇을 강조하느냐가 문서를 다르게 만든다.
- `examples/catalog.js`는 부품 호출법 참고용이다. 견본의 장 순서·조합을 문서에 옮기지 않는다.

### 선택 업그레이드 (기본 운용 — HTML은 처음엔 최소로)
처음엔 부품으로 빠르게 만들고, 사용자가 **고르는 장·박스만** 나중에 HTML 그림으로 바꾼다. PowerPoint에서 손으로 고친 파일에도 쓸 수 있다.
1. `python scripts/upgrade_box.py 결과.pptx --slide N --box K --info` → 박스 안쪽 크기와 현재 내용(차트 데이터·글)을 받는다.
2. 그 내용으로 HTML을 그린다 — 같은 데이터, 더 나은 표현(주석·조합·강조). 숫자를 새로 만들지 않는다.
3. `python scripts/render_html.py 그림.html 그림.png --fit W H` (1의 크기 그대로) → 렌더링 이미지를 열어 확인.
4. `python scripts/upgrade_box.py 결과.pptx --slide N --box K --image 그림.png --kind bar|line|diagram|…` → 안쪽만 교체, 원래 내용은 노트에 보존.
5. finalize 재실행 → 이미지가 바뀐 그 장만 다시 검수하면 된다(나머지는 이어받음).
- 업그레이드한 박스의 숫자는 그림이라 PowerPoint에서 못 고친다. 숫자가 바뀔 수 있는 박스는 업그레이드하지 않는다.

### HTML 시각화 모드 (선택 — 사용자가 원할 때만)
기본은 "숫자는 PPT 기본 차트·표, 그림은 HTML"이다. 사용자가 **"시각화는 전부 HTML로"**를 원하면 아래 규칙으로 허용한다.
- **언제 맞나:** 내부 검토·학습·빠른 공유처럼 받은 사람이 숫자를 고칠 일이 없는 문서. 보고 직전 수정이 잦은 임원 보고서엔 권하지 않는다(그림 속 숫자는 PowerPoint에서 못 고침).
- **크기는 1:1:** 박스 영역 크기를 `render_html.py --fit W H`(인치)로 그대로 그리고 `D.figureFit`으로 넣는다. 늘리거나 줄이지 않아야 그림 속 글자가 본문과 같은 크기가 된다. CSS 글자 크기는 pt × 1.333 = px (11pt ≈ 14.7px, 13pt ≈ 17.3px). 그림 속 최소 글자 10pt(13.3px).
- **표는 PPT 표로 유지:** 표는 HTML로 그려도 이점이 적고 수정만 어려워진다.
- **데이터는 노트에:** 그림에 들어간 숫자·출처는 슬라이드 노트에 그대로 적는다(누락 검사가 노트를 읽는다. 안 적으면 수치 누락으로 잡힌다).
- 색은 `D.THEME` 값을 CSS 변수로, 한국어 줄바꿈은 `word-break: keep-all` + 의미 단위 `<br>`. 그림 속 글자는 자동 검사가 못 보므로 렌더링 검수에서 더 꼼꼼히 본다.
- 그림마다 HTML 작성·렌더링·확인이 붙어 **토큰이 부품 대비 크게 늘어난다.** 장 수가 많으면 핵심 장만 HTML로 하는 게 낫다.

### 내용 충실도 최소 기준 (모델과 관계없이 지킨다)
- 스토리보드의 **박스마다 쓸 부품 이름을 적는다**(예: 좌 `chartBar` / 우 `flow`). 부품 없이 글만 쓰는 박스는 이유를 적는다.
- **본문 4장 이상이면 시각 유형 3종 이상**, 같은 주된 유형 3장 연속 금지, 글 위주 장은 본문의 40% 이하 — `check_richness.py`가 검사한다.
- 보고 모드에선 **장마다 숫자 근거 1개 이상 + 하단 출처(※)**. 숫자가 없으면 왜 없는지 적는다.
- 조사형 문서(원본 없이 만드는 문서)는 `research.md`에 **출처 5개 이상, 핵심 수치마다 출처**를 적은 뒤 스토리보드로 간다.
- 박스 하나에 들어갈 요소: 박스 메시지 + 시각 요소 1개 + 근거·해석 1~3줄. 박스가 비어 보이면 시각 요소를 키우지 말고 근거를 보탠다.

### 3단계 — 검수: 완료 게이트 통과 필수 (매번, 생략 불가)
**`python scripts/finalize.py 결과.pptx [원본파일 ...] [--ignore ...]` 가 `FINALIZE PASS`를 출력하기 전에는 작업이 끝난 것이 아니다.** 사용자에게 완료라고 말하지 않는다.

1. 1회차 실행 → 검사 5종(레이아웃·줄바꿈·문구·충실도·수치/사진 누락) + 렌더링(`render/slide-XX.png`) + `review.md` 양식 생성, 종료코드 2.
2. finalize가 알려주는 **모아보기 이미지(`render/todo-sheet-N.jpg`, 4장씩)를 한 번에 한 장씩 실제로 열어서 본다.** 글자가 작아 판단이 어려운 장만 `render/review/slide-XX.jpg`를 따로 연다. 렌더링 완료 메시지만 보고 넘어가지 않는다.
   - **이미지는 한 번의 요청에 한 장만 읽는다.** render 폴더를 통째로 읽거나 여러 이미지를 한꺼번에 넣지 않는다(Gemini CLI 등에서 입력 초과 400 오류, 토큰도 크게 낭비). 큰 원본 PNG(`slide-XX.png`)는 열지 않는다 — 해시 비교용이다. 장마다 `review.md`의 7개 항목을 실제로 본 내용으로 채운다:
   - 본 이미지(연 파일명 + slide 번호, 예: todo-sheet-1.jpg slide-02) / 넘침·잘림 / 줄바꿈(외톨이 줄·단어 중간 끊김) / 정렬(상자 위아래 끝·밑줄·도형 안 글자 중심) / 10초 질문(상무가 물을 질문) / 10초 답이 보이나 / 판정(OK 또는 수정 후 OK)
3. 문제가 보이면 PPT를 고치고 다시 생성 → finalize 재실행. 이미지가 **픽셀까지 같은 장은 이전 검수를 자동으로 이어받고, 바뀐 장만 다시 보라고 알려준다.** 알려준 장은 반드시 다시 연다.
4. 검사 이슈 0건 + 모든 장 검수 기록 완료일 때만 `FINALIZE PASS`.

검사별 의미와 고치는 법:
- 레이아웃: 박스 경계 침범·슬라이드 밖 도형. 카드·행 높이는 고정값이 아니라 `inner.h`에서 나눠 계산.
- 줄바꿈: 넘침, 외톨이 줄, 조사·괄호로 시작하는 줄, 숫자·단위 분리. 상자를 넓히기보다 문장을 줄이거나 의미 단위에서 직접 끊는다(`writing-style.md` '줄바꿈').
- 수치·사진 누락(원본 있을 때): 누락 후보는 주석·유첨에 넣는다. 의도적 제외(쪽 번호·문서 번호·개인 연락처·주소 번지)는 `--ignore`. 날짜 형식 차이로 뜬 후보는 확인만.
- 문구: 금지 표현, 핵심 메시지 길이, `[확인 필요]` 잔존.
- A3(`check_a3.py`, A3 장이 있을 때만): ③ 목표에 수치·기한, ⑥ 실행 계획에 담당·기한, ⑦ 효과 확인에 측정 지표 또는 측정 일정이 없으면 실패. 모르면 칸을 비워 [확인 필요]로 드러내면 통과(경고로 목록 표시).
- 근거 없는 일반론 문장이 없는지는 검수 기록을 쓸 때 같이 본다.

### 4단계 — 전달
답변 형식은 `author-preferences.md` 1절(결론 → 근거 → 신뢰도·리스크 → 코칭, [확인됨]/[일반론]/[추정])을 따른다.
파일과 함께 짧게: 장 구성(장·레이아웃·핵심 메시지 표), 남은 `[확인 필요]` 항목, 누락 검사 결과, 그리고 **finalize 출력의 `FINALIZE PASS ...` 줄을 그대로** 붙인다(사용자가 검수 완료를 확인하는 근거). PASS 줄이 없으면 전달하지 않는다.
사용자가 손으로 고친 디자인이 마음에 든다고 하면 `layouts-and-boxes.md` 패턴 표에 추가를 제안한다.

## 비용(토큰) 아끼기 — 기본으로 지킨다
토큰을 가장 많이 먹는 것은 ①이미지 보기 ②긴 원문·검색 결과 ③생성 코드 전체 재작성 ④수정 반복이다. 대화가 길어질수록 앞의 내용이 매번 다시 읽히므로 초반에 아낄수록 효과가 크다.
- **참고 문서는 필요한 것만:** 항상 `author-preferences.md` + 모드에 맞는 1~2개. 원본이 없으면 `source-analysis.md`는 생략, 손필기·수식이 없으면 `handwriting-and-math.md` 생략.
- **조사는 6회 안팎:** 검색 결과는 `research.md`에 요약하고 원문은 다시 읽지 않는다.
- **수정은 부분 편집으로:** 생성 스크립트를 통째로 다시 쓰지 말고 바뀌는 줄만 고친다. 장마다 함수로 나눠 두면 고칠 곳만 찾기 쉽다.
- **검수 이미지는 바뀐 장만:** finalize가 알려준 장만 연다. 전체 훑기가 필요하면 `render/contact.png` 한 장으로.
- **그림(HTML)은 한 번에 맞추기:** 정렬 규칙(`layouts-and-boxes.md`)대로 처음부터 그려 재렌더링 횟수를 줄인다.
- **체크포인트에서 방향 확정:** 다 만든 뒤 방향이 바뀌는 게 가장 비싸다.
- 사용 중인 도구가 모델을 바꿀 수 있으면, **원본 분석·조사·스토리보드는 상위 모델**(예: Opus, Gemini Pro), 반복 수정은 한 단계 낮은 모델(예: Sonnet, Gemini Flash)을 권한다. 가벼운 모델로 처음부터 끝까지 만들면 조사 깊이와 시각 다양성이 떨어지기 쉽다.

## 실행 환경 (Claude Code · Gemini CLI 공용)
- 이 스킬은 특정 AI 도구 전용 기능을 쓰지 않는다. 필요한 것은 셸 실행, 파일 읽기·쓰기, 이미지 보기, 웹 검색뿐이다.
- 필요 패키지: Node.js + `pptxgenjs`·`katex`(package.json), Python + requirements.txt 목록(`python-pptx`, `pillow`, `pdfplumber`, `python-docx`, `openpyxl`, `playwright`, `pymupdf`, Windows는 `pywin32`). 렌더링은 PowerPoint(Windows) 또는 LibreOffice.
- 스크립트 출력은 UTF-8이다. Windows 콘솔에서 글자가 깨지면 `set PYTHONIOENCODING=utf-8` 후 실행.
- 스크립트 경로는 이 SKILL.md가 있는 폴더 기준이다(`scripts/...`).
