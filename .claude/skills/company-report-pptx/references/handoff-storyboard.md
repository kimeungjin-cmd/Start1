# 외부 상위 모델과 나눠 쓰기 (스토리보드 넘겨받기)

실행 도구의 모델이 가벼울 때(예: CLI는 가벼운 모델만, 웹에 상위 모델) 쓰는 방식.
**생각은 상위 모델, 실행은 이 스킬.** 상위 모델이 만든 `storyboard.md`(와 `research.md`)를 받으면
1단계(원본 분석·조사·스토리보드)를 새로 하지 않고, 아래 형식을 지켰는지만 확인한 뒤 바로 2단계(PPT 생성)로 간다.

## 기본 흐름: 한 방향 (웹 → CLI, 왕복 없음)
1. **웹:** 원본만 올리고 요청문 붙여넣기 → 스토리보드를 받는다. 그림은 **원본 위치로** 적게 한다(`사진=4쪽`, `사진=3장#2`, `사진=12행`). 같은 쪽·장에 여러 개면 **위에서 아래, 왼쪽에서 오른쪽 순서로 #1 #2**. PDF의 선으로 그린 그래프·회로도도 그림으로 지목한다. 결과는 텍스트 복사, 또는 Google Docs로 내보내 .docx로 받아도 된다.
2. **CLI:** 받은 파일이 .docx·.pdf면 `python scripts/read_storyboard.py 받은파일 storyboard.md`로 바꾼다.
3. **CLI:** `python scripts/extract_assets.py 원본 assets` → 원본 그림이 번호와 위치로 정리된다.
4. **CLI:** 스토리보드의 원본 위치를 `python scripts/extract_assets.py --find "4쪽" assets`로 그림 번호로 바꿔 넣는다(같은 위치에 여럿이면 `#2`처럼 순서). 못 찾으면 멈추고 알린다.
5. 이후 생성·검사·finalize는 동일. 목록에 있는데 스토리보드에 안 쓰인 그림은 유첨으로.

웹이 PPT·워드에 그림까지 넣어 '완성본'을 만들게 하지 않는 이유: 원본 그림이 빠지거나 바뀌기 쉽고 [추정], 레이아웃·부품 정보가 사라져 실행 쪽이 다시 판단해야 하며, 원본 쪽 번호와의 추적이 끊긴다. 그림은 원본에서, 판단은 웹에서, 조립은 CLI에서.

## (선택) 그림 번호로 주고받기 — 그림이 많아 위치만으론 헷갈릴 때

1. 먼저 실행 쪽(CLI)에서 `python scripts/extract_assets.py 원본파일 assets` → 원본의 사진·그림·캡처 쪽이 `assets/P01.png…`로 나오고, 목록 `assets/assets_index.md`와 번호 붙은 모아보기 `assets/assets-sheet-N.jpg`가 생긴다.
2. **웹 모델에는** 원본 + `assets_index.md` + `assets-sheet-N.jpg`를 같이 올린다. 웹 모델은 원본을 직접 보고 분석하되, 그림은 스토리보드에 **번호로만** 적는다(`사진=P03`).
3. 표는 글이라 웹 모델이 스토리보드에 그대로 옮겨 적을 수 있다(`데이터=` 칸에 행 단위로). 그래프 그림의 숫자는 읽어 옮기지 말고 그림 번호를 쓴다.
4. 실행 쪽은 번호대로 `assets/P03.png`를 넣는다(`D.figure(..., "photo")`). 스토리보드에 없는 번호가 나오면 멈추고 알린다. **목록에 있는데 스토리보드에 안 쓰인 그림은 유첨으로**(사진 보존 원칙).

## 확인할 것 (빠졌으면 사용자에게 알리고 그 부분만 보완)
- 장마다: 레이아웃, 핵심 메시지, 박스별 [박스 제목 / 박스 메시지 / 부품 / 데이터 / 출처]
- 숫자마다 출처, 확인 안 된 값은 [확인 필요]
- [맞춤] 표시된 장 1~2개
- 스토리보드에 없는 숫자·사실을 만들어 넣지 않는다. 데이터가 부품에 맞지 않으면 바꾸지 말고 알린다.

## storyboard.md 형식
```
# 문서: (제목) / 대상: (상무 보고 | 파트장 보고 | 본인 학습 | 가족·개인) / 기준일: YYYY-MM-DD

## 1장 [맞춤]
- 레이아웃: 2-55            (1 | 2-55 | 2-64 | 2-73 | 3)
- 소제목: ...
- 핵심 메시지: ... (45자 이내, 결론)
- 부연설명: ...
- 박스1: 제목=... / 메시지=... / 부품=chartBar / 데이터=접점 용량 부족 7, 돌입전류 과다 3, 제조 불량 1 / 주석=1번 막대 "유력 원인" / 출처=회수품 분석(10/28)
- 박스2: 제목=... / 메시지=... / 부품=figure / 사진=P03 / 설명=불량 부위 빨간 원 / 출처=원본 4쪽
- (또는) 박스2: 제목=... / 메시지=... / 부품=flow / 데이터=배제 원인:제조 불량 배제(done); 유력 가설:접점 용량 부족(now); 확인 계획:재현시험 11/20(plan); 리스크:대체 검토 11/30(risk) / 출처=...
- 하단 출처: ※ ...

## 2장
...

## 유첨
- 유첨1: 원본 표 전체 / 부품=table / 데이터=...
```
부품 이름은 SKILL.md 부품표에 있는 것만 쓴다(chartBar, chartLine, chartDonut, kpis, timeline, flow, matrix, table, cards, rows, steps, checklist, equation, figure).

## 상위 모델(웹)에 붙여 넣을 요청문
```
아래 원본(첨부)으로 회사 보고용 PPT의 스토리보드를 만들어줘. PPT 파일은 만들지 말고, 정해진 형식의 텍스트만.
[독자] 최종 독자는 상무(결론 먼저, 논리적 근거, 검토 범위·판단 기준·배제한 것·확신도를 봄), 전달자는 파트장.
[원칙] 원본의 수치·사진은 버리지 않는다(본문에 못 넣으면 유첨). 원본에 없는 숫자·날짜·담당자는 만들지 말고 [확인 필요].
       원인 미확정은 배제 원인 → 유력 가설 → 확인 계획·날짜 → 리스크 조치. 숫자마다 출처.
[구성] 1장은 한 장 요약. 장마다 시각 요소 1개 이상, 본문 4장 이상이면 시각 유형 3종 이상, 핵심 장 1~2개는 [맞춤].
[부품] chartBar(순위) chartLine(추이·기준선) chartDonut(구성비) kpis(핵심 숫자) timeline(일정) flow(진행 단계)
       matrix(2기준 비교) table(항목×속성) cards(결론·추천) rows(속성 설명) steps(순서) checklist(확인 사항)
[레이아웃] 1 | 2-55 | 2-64 | 2-73 | 3  (기본 2-55, 왼쪽=근거 오른쪽=판단)
[그림] 그림·사진·캡처는 원본 위치로만 지목해(예: 사진=4쪽, 사진=3장#2, 사진=12행. 같은 쪽에 여러 개면 위에서부터 #1 #2). 그림 번호 목록(assets_index.md)을 같이 줬다면 번호(P01…)로 지목해. 그림 속 그래프 숫자를 새로 읽어 차트로 만들지 말 것. 번호 목록에 있는 그림은 본문이나 유첨에 전부 배정할 것.
[형식] (여기에 storyboard.md 형식 블록을 붙여 넣는다)
마지막에 원본에서 서로 안 맞는 부분과 확인 필요 질문을 따로 적어줘.
```

## 마지막 검토도 상위 모델에 (선택)
완성 후 `render/sheet-N.jpg`(4장 모아보기)를 웹에 올려 "상무가 10초 볼 때 물을 질문과, 답이 안 보이는 장"을 물으면 가벼운 모델의 검수를 보완할 수 있다.
